# Архитектура и спецификация: Транспортный режим Fake Video Track (`media_video`) в WebRTC/JVB

Документация актуальна для `ANet v0.7.3+` (ветка `dev/rtt`).

---

## 1. Концепция и назначение

Режим `wrtc_mode = "media_video"` — это механизм маскировки VPN-туннеля под легитимный медиа-видеопоток WebRTC (кодек **VP8** поверх **SRTP / DTLS 1.2 / UDP**) в комнатах корпоративных ВКС (Ktalk / Jitsi Meet).

### Главное отличие от стандартных транспортов:
* **Нулевая видимость для ТСПУ и DPI:** Трафик идёт не на неизвестный зарубежный VPS, а на официальные серверы видеоконференций (в Ktalk это медиа-мосты Jitsi Videobridge — JVB, например, `89.169.16.0/24`, UDP-порты `10000–10010` и STUN/TURN `34788`).
* **Топология "Звезда" через SFU (Selective Forwarding Unit):** Клиент и сервер являются участниками одной конференции Jitsi. Медиа-сервер JVB принимает исходящий видеопоток от каждого участника и реплицирует его (broadcast) всем остальным абонентам комнаты.
* **Сквозная криптографическая изоляция:** Медиа-мост видит только валидные ключевые кадры видео VP8 с корректными заголовками RTP (90 кГц) и VP8 Payload Descriptor. Полезные сетевые IP-пакеты туннеля зашифрованы персональным симметричным шифром ASTP (ChaCha20-Poly1305) и снабжены 2-байтным идентификатором сессии (`client_tag`).

---

## 2. Структура сетевого пакета (Wire Format)

Каждый зашифрованный сетевой пакет передаётся внутри ключевого кадра VP8:

```text
+--------------------------------------------------------------------------------------------------------------------+
|                                           L4: UDP Datagram                                                         |
+--------------------------------------------------------------------------------------------------------------------+
|                                      SRTP Packet (RFC 3711 / RFC 5764)                                             |
+--------------------------+---------------------------+---------------------+---------------------------------------+
| RTP Header (12 байт)     | VP8 Descriptor (1 байт)   | VP8 Keyframe Header | Зашифрованная полезная нагрузка ASTP  |
| V=2, P=0, M=1, PT=100/96 | 0x10 (Keyframe start)     | (10 байт сигнатуры) | + MAC аутентификации                  |
| Seq, Timestamp (90kHz),  |                           |                     |                                       |
| SSRC                     |                           |                     |                                       |
+--------------------------+---------------------------+---------------------+-------------------+-------------------+
                                                                             | Client Tag (2B)   | ASTP Envelope     |
                                                                             | u16 Big-Endian    | Nonce (12B)       |
                                                                             | [ip_2, ip_3]      | Ciphertext        |
                                                                             |                   | Poly1305 MAC (16B)|
                                                                             +-------------------+-------------------+
```

### Формирование `client_tag`:
Для исключения коллизий ключей шифрования при широковещательной рассылке кадров через JVB сервер и клиент используют детерминированный тег:
$$\text{client\_tag} = (ip_2 \ll 8) \mid ip_3$$
где $ip_2, ip_3$ — два младших октета назначенного туннельного IPv4-адреса клиента.
* Для IP `172.112.224.5` $\to$ тег `0xE005`.
* Для IP `172.112.224.7` $\to$ тег `0xE007`.

**Алгоритм фильтрации:**
1. При получении видеокадра от JVB клиент считывает первые 2 байта полезной нагрузки.
2. Если `tag != my_client_tag`, пакет немедленно и бесшумно отбрасывается за $O(1)$ без попыток расшифровки.
3. Сервер по `client_tag` мгновенно находит структуру сессии клиента в `clients_by_tag: Arc<DashMap<u16, Arc<ClientTransportInfo>>>`.

## 3. Решение ключевых проблем и стабильность соединения

В ходе эксплуатации и нагрузочного тестирования были локализованы и устранены критические архитектурные уязвимости конвейера WebRTC:

### 3.1. Устранение гонки маршрутизации при реконнекте (`session_id race`)
* **Симптом:** Трафик внезапно прекращался при реконнекте одного из клиентов; при этом на клиенте не было ошибок, а сервер переставал маршрутизировать пакеты от ядра в туннель.
* **Причина:** При отключении сокета (WebSocket, SSH или предыдущего экземпляра туннеля) метод `suspend_client` / `remove_client` удалял записи из `quic_router` и `clients_by_ip` по ключу IP без проверки владельца. Если этот IP в ту же миллисекунду выдавался новому подключению, старый отложенный обработчик сносил рабочий роутер нового клиента.
* **Решение:** Внедрена атомарная проверка владения IP:
  ```rust
  let is_current = if let Some(current) = self.clients_by_ip.get(client_ip) {
      current.session_id == client_info.session_id
  } else {
      true
  };
  if is_current {
      self.quic_router.remove(client_ip);
      // ...
  }
  ```

### 3.2. Очистка состояния WRTC-комнаты при переподключении JVB
* **Симптом:** При разрыве соединения JVB (таймаут сессии комнаты или сетевой сбой) сервер перевходил в комнату, но старые клиенты оставались в таблице тегов, а воркер приёма видеокадров читал закрытый стрим.
* **Решение:**
    * Фоновый воркер `video_uplink_task` принудительно прерывается (`abort()`) при выходе из цикла комнаты.
    * Таблицы `clients_by_tag`, `client_modes`, `client_video_endpoints` полностью очищаются.
    * Флаг `first_server_rx` корректно сбрасывается для нового цикла приёма.

### 3.3. Валидация Ping/Pong по живому реестру
* **Симптом:** Клиент продолжал получать `anet_pong` по каналу Colibri WebSocket от JVB, даже если его сессия на сервере была выселена по таймауту неактивности, из-за чего клиент не предпринимал попыток реконнекта.
* **Решение:** Сервер отправляет `anet_pong` только в том случае, если сессия клиента **реально активна в реестре** (`reg_clone.is_session_active`). Если сессия выселена, pong не отправляется, и клиент через 45 секунд штатно инициирует чистый реконнект.

## 4. Верификация через `tcpdump` и Wireshark

Для подтверждения того, что трафик маскируется под видеопоток, используется захват сетевых пакетов.

### Быстрая проверка в консоли:
```bash
# Проверка наличия RTP-заголовков (байт 0x80) на портах медиа-моста Ktalk
sudo tcpdump -ni any "udp and (net 89.169.16.0/24 or port 34788) and greater 200" -c 20 -X
```

### Запись и анализ дампа в Wireshark:
```bash
sudo tcpdump -ni any "udp and (net 89.169.16.0/24 or port 34788)" -w /tmp/wrtc_video.pcap -c 1000
```

### Результаты анализа реального дампа:
При исследовании дампа сессии зафиксированы:
1. **Сетевые эндпоинты:**
    * **Клиент:** `89.110.67.85:53644` (UDP)
    * **Медиа-сервер JVB:** `89.169.16.19:10006` (UDP, СКБ Контур / Ktalk)
2. **ICE/STUN согласование:**
    * Обмен пакетами STUN Binding Request / Response с атрибутом `USERNAME: 8a82j1k57h7rjc:kvvSBNmGgloKIgxv` (библиотека `ice4j.org`).
3. **DTLS Handshake:**
    * Согласование ключей SRTP через `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`.
4. **Медиа-поток (RTP over SRTP):**
    * **Video Track:** Пакеты Payload Type `100` (VP8) с тактовой частотой 90 кГц и размером 1200–1400 байт.
    * **Audio Keepalive:** Пакеты Payload Type `111` (Opus) размером ~70–90 байт с интервалом 20 мс.

Для внешнего наблюдателя трафик на 100% соответствует штатному видеозвонку в сервисе Ktalk.
