# Архитектура и спецификация: Транспортный режим Fake Video Track (`media_video`) в WebRTC/JVB

Документация актуальна для `ANet v0.7.5+` (ветка `dev/xwrtc`).

---

## 1. Концепция и назначение

Режим `wrtc_mode = "media_video"` (и `wrtc_mode = "auto"` при активном видеоканале) — это механизм инкапсуляции туннельного трафика в стандартный медиа-видеопоток WebRTC (кодек **VP8** поверх **SRTP / DTLS 1.2 / UDP**) в комнатах корпоративных сервисов видеоконференцсвязи (Ktalk / Jitsi Meet).

### Главное отличие от стандартных транспортов:
* **Стабильность маршрутизации на промежуточных узлах:** Трафик передаётся через штатные серверы видеоконференций (медиа-мосты Jitsi Videobridge — JVB, например, `89.169.16.0/24`, UDP-порты `10000–10010` и STUN/TURN `34788`), что исключает проблемы с соединением на нестабильных внешних магистралях.
* **Топология «Звезда» через SFU (Selective Forwarding Unit):** Клиент и сервер являются участниками одной конференции Jitsi. Медиа-сервер JVB принимает исходящий видеопоток от каждого участника и реплицирует его (forward) подписчикам комнаты.
* **Сквозная криптографическая изоляция:** Медиа-мост обрабатывает валидные кадры видео VP8 (FullHD `1920x1080`) с корректными заголовками RTP (90 кГц) и расширенным VP8 Payload Descriptor (RFC 7741). Полезные сетевые IP-пакеты туннеля зашифрованы персональным симметричным шифром ASTP (ChaCha20-Poly1305) и снабжены 2-байтным идентификатором сессии (`client_tag`).

## 2. Структура сетевого пакета (Wire Format, протокол `video_v2`)

Каждый зашифрованный сетевой пакет (или микро-батч пакетов) передаётся внутри RTP-пакета видеодорожки VP8 с 26-байтным префиксом (`VP8_ASTP_PREFIX_LEN = 26`):

```text
+----------------------------------------------------------------------------------------------------------------------------+
|                                                 L4: UDP Datagram                                                           |
+----------------------------------------------------------------------------------------------------------------------------+
|                                            SRTP Packet (RFC 3711 / RFC 5764)                                               |
+-----------------------+---------------------------+--------------------------+---------------------------------------------+
| RTP Header (12 байт)  | VP8 Descriptor (4 байта)  | VP8 Frame Header (20 Б)  | Тег клиента + Зашифрованный ASTP-конверт    |
| V=2, P=0, M=1         | RFC 7741:                 | Keyframe 1080p (0x30...) |                                             |
| PT=100/96             | [0x90, 0x80,              | или Interframe (0x31...) |                                             |
| Seq, Timestamp(90kHz) |  0x80 | (pic_id >> 8),    | + 10B сигнатура хвоста   |                                             |
| SSRC                  |  pic_id & 0xFF]           | VP8_HEADER_TAIL_MAGIC    |                                             |
+-----------------------+---------------------------+--------------------------+-------------------+-------------------------+
                                                                               | Client Tag (2 Б)  | ASTP Envelope           |
                                                                               | u16 Big-Endian    | Nonce (12 Б)            |
                                                                               | [ip_2, ip_3]      | Ciphertext (IP / Batch) |
                                                                               |                   | Poly1305 MAC (16 Б)     |
                                                                               +-------------------+-------------------------+
```

### 2.1. Структура 26-байтного префикса (`VP8_ASTP_PREFIX_LEN`)
1. **VP8 Payload Descriptor (`4 байта`, RFC 7741):**
   * `payload[0] = 0x90` — бит расширения `X=1` (`0x80`) + бит начала партиции `S=1` (`0x10`).
   * `payload[1] = 0x80` — бит наличия `PictureID` (`I=1`).
   * `payload[2..4]` — 15-битный монотонно растущий `PictureID` с установленным старшим битом `M=1` (`0x8000 | pic_id`).
   * На приёмной стороне дескриптор произвольной длины разбирается и отсекается по стандарту RFC 7741 функцией `strip_vp8_payload_descriptor()`.
2. **VP8 Frame Header (`20 байт`):**
   * В режиме `video_v2 = true` чередуются два типа заголовков с разрешением `1920x1080` (FullHD):
     * **`VP8_KEYFRAME_1080P_HEADER`** (`0x30, 0x01, 0x00, 0x9d, 0x01, 0x2a, 0x80, 0x07, 0x38, 0x04, ...`) — ключевой кадр (I-frame). Отправляется на старте сессии, по запросу `force_next_keyframe()` и далее каждый 32-й пакет (`(frame_num & 31) == 0`). Заявленное в заголовке разрешение `1920x1080` предотвращает искусственное занижение пропускной способности контроллером `BitrateController` внутри JVB.
     * **`VP8_INTERFRAME_HEADER`** (`0x31, ...`) — межкадровый пакет (P-frame, `bit 0 = 1`). Отправляется для остальных 31 из 32 пакетов, чтобы SFU JVB не сбрасывал `Vp8FrameMap` и не пересоздавал контекст проекции видеопотока на каждом RTP-пакете.
   * На приёме заголовок проверяется функцией `is_valid_vp8_frame_header()` по стартовым байтам и 10-байтной сигнатуре хвоста `VP8_HEADER_TAIL_MAGIC`.
   * **Пакеты прогрева (`VIDEO_WARMUP_PAYLOAD`):** 16-байтный кадр прогрева (`[0x00, 0xFF, 0xFF, 0...]`) распознаётся клиентом и сервером как внутритуннельный маркер готовности видеоканала (`video_warmed_up = true`) и отбрасывается до передачи в TUN.
3. **Идентификатор сессии `client_tag` (`2 байта`):**
   * Для исключения коллизий ключей шифрования при широковещательной рассылке кадров через JVB сервер и клиент используют детерминированный тег из двух младших октетов назначенного туннельного IPv4-адреса:
     $$\text{client\_tag} = (ip_2 \ll 8) \mid ip_3$$
     * Для IP `172.112.224.5` $\to$ тег `0xE005`.
     * Для IP `172.112.224.7` $\to$ тег `0xE007`.
   * **Алгоритм фильтрации $O(1)$:**
     * Клиент читает первые 2 байта после заголовка VP8 и при `pkt_tag != my_client_tag` (и `pkt_tag != TAG_UNTAGGED`) мгновенно отбрасывает чужой кадр без попыток расшифровки.
     * Сервер по `client_tag` за $O(1)$ находит контекст клиента в `clients_by_tag: Arc<DashMap<u16, Arc<ClientTransportInfo>>>`.

### 2.2. Формат полезной нагрузки внутри ASTP (одиночный пакет и микро-батчинг)
В режиме `video_v2` перед шифрованием ChaCha20-Poly1305 отключён случайный паддинг, а малые IP-пакеты автоматически агрегируются в микро-батчи:
* **Одиночный IP-пакет:** начинается со стандартного заголовка IPv4 (`0x4x`) или IPv6 (`0x6x`).
* **Микро-батч (`VIDEO_BATCH_MARKER = 0x00`):** если в очереди туннеля есть несколько пакетов и суммарный размер не превышает `max_video_batch_bytes` (по умолчанию `1260` байт для прямого подключения и `960` байт при маршрутизации через Cloudflare WARP; до `video_batch_max_packets = 16` пакетов за раз), формируется буфер:
  ```text
  [0x00 (1B)][len_1: u16 BE][ip_pkt_1][len_2: u16 BE][ip_pkt_2]...
  ```
  Поскольку ни один валидный IPv4/IPv6 пакет не начинается с байта `0x00`, приёмник однозначно отличает микро-батч от одиночного пакета и распаковывает его через `unpack_batch(&decrypted[1..])`.

### 2.3. Автоматическая корректировка MTU туннеля (`video_mtu_overhead = 110`)
Для предотвращения IP-фрагментации UDP-датаграмм WebRTC на промежуточных шлюзах и в туннельных интерфейсах (таких как `wgcf-profile` с MTU 1280) эффективный MTU туннеля автоматически рассчитывается с вычетом `video_mtu_overhead = 110` байт и нижней границей `min_tun_mtu = 900` байт:
$$\text{TUN\_MTU} = \max(\text{server\_mtu} - \text{video\_mtu\_overhead}, \text{min\_tun\_mtu})$$
Запас `110` байт включает полный сетевой оверхед:
* `20 байт` (внешний заголовок IPv4) + `8 байт` (UDP) + `16 байт` (SRTP Auth Tag / MKI) + `12 байт` (RTP Header) + `24 байта` (VP8 Descriptor + Frame Header) + `2 байта` (`client_tag`) + `28 байт` (ASTP Nonce + Poly1305 MAC) = **110 байт**.
* При прямом соединении (`[network] mtu = 1400`) эффективный MTU туннеля составляет `1290` байт (`max_video_batch_bytes = 1260`).
* При стабилизации маршрута сервера через Cloudflare WARP (`[network] mtu = 1100`, `wgcf-profile` MTU `1280`) эффективный MTU туннеля составляет `990` байт (`max_video_batch_bytes = 960`), что гарантирует прохождение каждого RTP-пакета внутри WireGuard без фрагментации.

## 3. Архитектура конвейера высокой пропускной способности (EDT Micro-Pacer и сериализация RTP)

Для достижения стабильной скорости 100–200+ Мбит/с через медиа-мост JVB без потерь пакетов и переполнения буферов реализованы следующие механизмы:

### 3.1. Zero-Copy формирование пакета в едином буфере (`wrap_packet_slice_with_headroom`)
На горячем пути отправки (`anet-common/src/transport.rs` $\to$ `WrtcPeer::send_video_frame_preallocated`) исключены промежуточные аллокации и копирования памяти:
1. Функция `wrap_packet_slice_with_headroom()` выделяет единый `BytesMut` ёмкостью `26 + 12 + payload.len() + 16`, сразу оставляя 26 байт (`VP8_ASTP_PREFIX_LEN`) в начале буфера, и шифрует полезную нагрузку ChaCha20-Poly1305 на месте (`encrypt_in_place_detached`).
2. Метод `send_video_frame_preallocated()` записывает 4 байта дескриптора VP8, 20 байт заголовка кадра VP8 и 2 байта `client_tag` непосредственно в зарезервированные первые 26 байт этого же буфера, после чего вызывает `payload.freeze()` и передаёт `Bytes` в `video_track.write_rtp()`.

### 3.2. Строгая сериализация RTP `(seq, pic_id, timestamp)` при многопоточной отправке
Когда несколько асинхронных задач параллельно отправляют видеокадры, несинхронизированный инкремент счётчика и вызов `write_rtp()` приводили бы к тому, что пакет с `seq = N+1` попадал в сокет раньше `seq = N`. На стороне SFU JVB и в `wgcf-profile` это вызывало ложные срабатывания детектора потерь (NACK) и сброс кадров в `Vp8FrameMap`.
* В `WrtcPeer::send_video_frame_preallocated()` генерация `(sequence_number, pic_id, timestamp)` и вызов `video_track.write_rtp()` выполняются строго атомарно внутри критической секции `video_send_lock`:
  * `sequence_number = (frame_num & 0xFFFF) as u16`
  * `pic_id = (frame_num & 0x7FFF) as u16`
  * `timestamp = frame_num.wrapping_mul(300)` (шаг 300 тиков при частоте 90 кГц)

### 3.3. Микро-пейсер EDT (Earliest Departure Time) с горизонтом под 1 мс таймер Tokio
При чтении пачки пакетов из TUN (`uplink_burst_max_packets = 64`) мгновенный залп десятков UDP-пакетов за несколько микросекунд переполняет входные очереди сетевой карты, сокета `wgcf-profile` или буфера JVB.
В `anet-client-core/src/transport/wrtc.rs` и `anet-server/src/servers/wrtc.rs` внедрён **EDT-пейсер**:
* Каждому отправляемому кадру длиной $L$ байт назначается расчётное время отправки:
  * **Uplink (клиент $\to$ JVB):** `WRTC_UPLINK_PACING_NS_PER_BYTE = 45` нс/байт (~177 Мбит/с).
  * **Downlink (сервер $\to$ JVB):** `WRTC_DOWNLINK_PACING_NS_PER_BYTE = 38` нс/байт (~210 Мбит/с).
* Поскольку стандартное колесо таймеров Tokio имеет разрешение **1 мс**, вызов `tokio::time::sleep` на каждые 50 мкс ограничивал бы скорость до ~10 Мбит/с. Поэтому используется **горизонт коалесценции `WRTC_PACING_HORIZON_NS = 2_500_000` (2.5 мс)**: пакеты уходят без ожидания, пока накопленный «долг» времени отправки не превысит 2.5 мс, после чего выполняется один точный `sleep` на ~1–2 мс. Это обеспечивает плавный поток UDP на скоростях до 200 Мбит/с без микровсплесков.

### 3.4. Безусловная доставка в/из TUN, устранение Bufferbloat и тюнинг 1-vCPU VPS
* **Отказ от `try_send` на каналах TUN:** Воркеры приёма видеопотока (`video_rx`) и резервных каналов используют асинхронный `send().await` с обратным давлением (backpressure) вместо `try_send`, что полностью исключает тихое отбрасывание расшифрованных TCP-сегментов внутри клиента и сервера при пиковой нагрузке.
* **Компактный `tokio::io::duplex` (`WRTC_DUPLEX_BUFFER_SIZE = 256 KiB`):** Размер внутреннего буфера обмена между ASTP-сессией и воркерами сокетов уменьшен с 4 МиБ до 256 КиБ, что устраняет многосекундный Bufferbloat и удерживает RTT под нагрузкой стабильным.
* **Тюнинг потоков на маломощных VPS (`anet-server/src/main.rs`):** На серверах с 1–2 ядрами vCPU количество рабочих потоков Tokio и `reactor_pool_size` автоматически ограничивается числом физических ядер (минимум 2), избавляя планировщик Linux от лишних переключений контекста при интенсивном шифровании SRTP + ChaCha20-Poly1305.
* **Системные буферы `SO_RCVBUF` / `SO_SNDBUF` (8 МиБ):** Среда `TunedTokioRuntime` автоматически выставляет буферы каждого UDP-сокета WebRTC в `8 MiB` (`udp_socket_buffer_size = 8388608`).

## 4. Стабильность сессий, развязка жизнеспособности каналов и очистка состояния

### 4.1. Развязка `media_video` от кратковременных сбоев `Colibri-WS` (`colibri_ws_read_timeout_secs = 25`)
* При работе через сложные сетевые маршруты (или туннель Cloudflare WARP) TCP-соединение управляющего канала `Colibri-WS` может кратковременно «замирать» из-за потерь TCP-сегментов, в то время как UDP-поток `media_video` продолжает штатно передавать пакеты.
* В `WrtcPeer` реализовано **независимое фоновое переподключение `Colibri-WS`**:
  1. Если из `Colibri-WS` нет входящих кадров дольше `colibri_ws_read_timeout_secs` (`25 с`), фоновая задача тихо переоткрывает WebSocket к тому же URL JVB (с быстрым перебором исходных TCP-портов) и заново отправляет `ReceiverVideoConstraints`.
  2. Пока по UDP продолжают поступать видеокадры (`last_video_rx_ms` обновляется не реже чем раз в 15 секунд), сторожевой таймер `check_dead_reason()` **не разрывает** сессию `WrtcPeer` даже при временной недоступности `Colibri-WS`.

### 4.2. Автоматическое переключение `MediaVideo` $\leftrightarrow$ `Colibri-WS` при потере UDP
Если на маршруте клиента возникают проблемы с прохождением UDP-пакетов:
1. **На стороне клиента:** признак активности видеоканала (`video_warmed_up`) требует одновременного выполнения трёх условий: получен хотя бы один видеокадр от сервера, активно UDP ICE-соединение (`peer.is_connected == true`) и с момента последнего входящего UDP-видеокадра прошло не более **5 секунд**. При нарушении любого условия клиент мгновенно переводит отправку в `PacketBatcher` поверх `Colibri-WS` (`WrtcMessage::AstpBatch`).
2. **На стороне сервера (защита от асимметричной потери UDP):** при получении от клиента любого пакета `AstpBatch` по `Colibri-WS` сервер фиксирует метку `client_last_ws_batch_ms`, сбрасывает `client_video_warmed_up` для данного `client_tag` и направляет ответный Downlink-трафик через `Colibri-WS` (`AstpBatch`), сохраняя двустороннюю связь.

### 4.3. Корректный выход из комнаты (`leave_room`) и защита от «призрачных» источников
* При завершении сессии метод `XmppSession::leave_room()` отправляет в Jicofo:
  1. `<jingle action="source-remove" ...>` с локальными `audio` и `video` SSRC;
  2. `<jingle action="session-terminate" ...><reason><success/></reason></jingle>`;
  3. `<presence type="unavailable" xmlns="jabber:client"/>` в MUC-комнату;
  4. Выдерживает паузу `120 мс` перед закрытием потока `<close/>`, чтобы Prosody гарантированно доставил IQ-станзы в Jicofo.

## 5. Диагностика с помощью `tcpdump` и Wireshark

### Быстрая проверка в консоли:
```bash
# Проверка наличия RTP-заголовков (байт 0x80/0x90) на портах медиа-моста Ktalk
sudo tcpdump -ni any "udp and (net 89.169.16.0/24 or port 34788) and greater 200" -c 20 -X
```

### Характеристики трафика в дампе:
1. **ICE/STUN согласование:** Обмен пакетами STUN Binding Request / Response с атрибутом `USERNAME` (стек `ice4j.org` на стороне JVB).
2. **DTLS 1.2 Handshake:** Согласование ключей SRTP через `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`.
3. **Медиа-поток (RTP over SRTP):**
   * **Video Track:** Пакеты Payload Type `100` (или `96`, VP8) с тактовой частотой 90 кГц, строго монотонным приростом Sequence Number (+1) и Timestamp (+300 на пакет) и фоновым keepalive при простое.
   * **Audio Keepalive:** Пакеты Payload Type `111` (Opus silence `0xf8, 0xff, 0xfe`) размером ~70–90 байт с интервалом 20 мс (48 кГц).
