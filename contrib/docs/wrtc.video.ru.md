# Архитектура и спецификация: Транспортный режим Fake Video Track (`media_video`) в WebRTC/JVB

Документация актуальна для `ANet v0.7.4+` (ветка `master`).

---

## 1. Концепция и назначение

Режим `wrtc_mode = "media_video"` (и `wrtc_mode = "auto"` при активном видеоканале) — это механизм маскировки VPN-туннеля под легитимный медиа-видеопоток WebRTC (кодек **VP8** поверх **SRTP / DTLS 1.2 / UDP**) в комнатах корпоративных ВКС (Ktalk / Jitsi Meet).

### Главное отличие от стандартных транспортов:
* **Нулевая видимость для ТСПУ и DPI:** Трафик идёт не на неизвестный зарубежный VPS, а на официальные серверы видеоконференций (в Ktalk это медиа-мосты Jitsi Videobridge — JVB, например, `89.169.16.0/24`, UDP-порты `10000–10010` и STUN/TURN `34788`).
* **Топология «Звезда» через SFU (Selective Forwarding Unit):** Клиент и сервер являются участниками одной конференции Jitsi. Медиа-сервер JVB принимает исходящий видеопоток от каждого участника и реплицирует его (forward) подписчикам комнаты.
* **Сквозная криптографическая изоляция:** Медиа-мост видит только валидные кадры видео VP8 (FullHD `1920x1080`) с корректными заголовками RTP (90 кГц) и расширенным VP8 Payload Descriptor (RFC 7741). Полезные сетевые IP-пакеты туннеля зашифрованы персональным симметричным шифром ASTP (ChaCha20-Poly1305) и снабжены 2-байтным идентификатором сессии (`client_tag`).

---

## 2. Структура сетевого пакета (Wire Format, протокол `video_v2`)

Каждый зашифрованный сетевой пакет (или микро-батч пакетов) передаётся внутри RTP-пакета видеодорожки VP8 с 26-байтным префиксом (`VP8_ASTP_PREFIX_LEN = 26`):

```text
+----------------------------------------------------------------------------------------------------------------------------+
|                                                 L4: UDP Datagram                                                           |
+----------------------------------------------------------------------------------------------------------------------------+
|                                            SRTP Packet (RFC 3711 / RFC 5764)                                               |
+-----------------------+---------------------------+--------------------------+---------------------------------------------+
| RTP Header (12 байт)  | VP8 Descriptor (4 байта)  | VP8 Frame Header (20 Б)  | Тег клиента + Зашифрованный ASTP-конверт    |
| V=2, P=0, M=1         | RFC 7741:                 | Keyframe 1080p (0x30...) |                                             |
| PT=100/96             | [0x90, 0x80,              | или Interframe (0x31...) |                                             |
| Seq, Timestamp(90kHz) |  0x80 | (pic_id >> 8),    | + 10B сигнатура хвоста   |                                             |
| SSRC                  |  pic_id & 0xFF]           | VP8_HEADER_TAIL_MAGIC    |                                             |
+-----------------------+---------------------------+--------------------------+-------------------+-------------------------+
                                                                               | Client Tag (2 Б)  | ASTP Envelope           |
                                                                               | u16 Big-Endian    | Nonce (12 Б)            |
                                                                               | [ip_2, ip_3]      | Ciphertext (IP / Batch) |
                                                                               |                   | Poly1305 MAC (16 Б)     |
                                                                               +-------------------+-------------------------+
```

### 2.1. Структура 26-байтного префикса (`VP8_ASTP_PREFIX_LEN`)
1. **VP8 Payload Descriptor (`4 байта`, RFC 7741):**
   * `payload[0] = 0x90` — бит расширения `X=1` (`0x80`) + бит начала партиции `S=1` (`0x10`).
   * `payload[1] = 0x80` — бит наличия `PictureID` (`I=1`).
   * `payload[2..4]` — 15-битный монотонно растущий `PictureID` с установленным старшим битом `M=1` (`0x8000 | pic_id`).
   * На приёмной стороне дескриптор произвольной длины разбирается и отсекается по стандарту RFC 7741 функцией `strip_vp8_payload_descriptor()`.
2. **VP8 Frame Header (`20 байт`):**
   * В режиме `video_v2 = true` чередуются два типа заголовков с разрешением `1920x1080` (FullHD):
     * **`VP8_KEYFRAME_1080P_HEADER`** (`0x30, 0x01, 0x00, 0x9d, 0x01, 0x2a, 0x80, 0x07, 0x38, 0x04, ...`) — ключевой кадр (I-frame). Отправляется на старте сессии, по запросу `force_next_keyframe()` и далее каждый 32-й пакет (`(frame_num & 31) == 0`). Заявленное в заголовке разрешение `1920x1080` предотвращает искусственное занижение пропускной способности контроллером `BitrateController` внутри JVB.
     * **`VP8_INTERFRAME_HEADER`** (`0x31, ...`) — межкадровый пакет (P-frame, `bit 0 = 1`). Отправляется для остальных 31 из 32 пакетов, чтобы SFU JVB не сбрасывал `Vp8FrameMap` и не пересоздавал контекст проекции видеопотока на каждом RTP-пакете.
   * На приёме заголовок проверяется функцией `is_valid_vp8_frame_header()` по стартовым байтам и 10-байтной сигнатуре хвоста `VP8_HEADER_TAIL_MAGIC`. Пустые keepalive-кадры (содержащие только `4 + 20 = 24` байта без ASTP-нагрузки) отбрасываются после поддержания активности RTP-потока в JVB.
3. **Идентификатор сессии `client_tag` (`2 байта`):**
   * Для исключения коллизий ключей шифрования при широковещательной рассылке кадров через JVB сервер и клиент используют детерминированный тег из двух младших октетов назначенного туннельного IPv4-адреса:
     $$\text{client\_tag} = (ip_2 \ll 8) \mid ip_3$$
     * Для IP `172.112.224.5` $\to$ тег `0xE005`.
     * Для IP `172.112.224.7` $\to$ тег `0xE007`.
   * **Алгоритм фильтрации $O(1)$:**
     * Клиент читает первые 2 байта после заголовка VP8 и при `pkt_tag != my_client_tag` (и `pkt_tag != TAG_UNTAGGED`) мгновенно отбрасывает чужой кадр без попыток расшифровки.
     * Сервер по `client_tag` за $O(1)$ находит контекст клиента в `clients_by_tag: Arc<DashMap<u16, Arc<ClientTransportInfo>>>`.

### 2.2. Формат полезной нагрузки внутри ASTP (одиночный пакет и микро-батчинг)
В режиме `video_v2` перед шифрованием ChaCha20-Poly1305 отключён случайный stealth-паддинг, а малые IP-пакеты автоматически агрегируются в микро-батчи:
* **Одиночный IP-пакет:** начинается со стандартного заголовка IPv4 (`0x4x`) или IPv6 (`0x6x`).
* **Микро-батч (`VIDEO_BATCH_MARKER = 0x00`):** если в очереди туннеля есть несколько пакетов и суммарный размер не превышает `MAX_VIDEO_BATCH_BYTES = 1300` байт (до 16 пакетов за раз), формируется буфер:
  ```text
  [0x00 (1B)][len_1: u16 BE][ip_pkt_1][len_2: u16 BE][ip_pkt_2]...
  ```
  Поскольку ни один валидный IPv4/IPv6 пакет не начинается с байта `0x00`, приёмник однозначно отличает микро-батч от одиночного пакета и распаковывает его через `unpack_batch(&decrypted[1..])`.

### 2.3. Автоматическая корректировка MTU туннеля
Для предотвращения IP-фрагментации UDP-датаграмм WebRTC на клиенте после получения `auth_response.mtu` от сервера MTU TUN-интерфейса автоматически уменьшается на константу `WRTC_VIDEO_MTU_OVERHEAD = 60` байт (с нижней границей `1200` байт):
$$\text{TUN\_MTU} = \max(\text{server\_mtu} - 60, 1200)$$
Эти 60 байт учитывают 26 байт префикса `VP8 + Client Tag` и ~34 байта заголовков `RTP + Extensions + SRTP Auth Tag`.

## 3. Архитектура конвейера высокой пропускной способности

Для достижения пропускной способности 40–65+ Мбит/с через медиа-мост JVB без потерь пакетов и лишней нагрузки на CPU реализованы следующие механизмы:

### 3.1. Zero-Copy формирование пакета в едином буфере (`wrap_packet_slice_with_headroom`)
На горячем пути отправки (`anet-common/src/transport.rs` $\to$ `WrtcPeer::send_video_frame_preallocated`) исключены промежуточные аллокации и копирования памяти:
1. Функция `wrap_packet_slice_with_headroom()` выделяет единый `BytesMut` ёмкостью `26 + 12 + payload.len() + 16`, сразу оставляя 26 байт (`VP8_ASTP_PREFIX_LEN`) в начале буфера, и шифрует полезную нагрузку ChaCha20-Poly1305 на месте (`encrypt_in_place_detached`).
2. Метод `send_video_frame_preallocated()` записывает 4 байта дескриптора VP8, 20 байт заголовка кадра VP8 и 2 байта `client_tag` непосредственно в зарезервированные первые 26 байт этого же буфера, после чего вызывает `payload.freeze()` и передаёт `Bytes` в `video_track.write_rtp()`.

### 3.2. Монотонный генератор `(seq, pic_id, timestamp)` без коллизий при бурстах
При отправке нескольких пакетов в течение одной миллисекунды расчёт RTP Timestamp от системных часов приводил бы к одинаковым `timestamp` у разных `sequence_number`, из-за чего `Vp8FrameMap` в JVB отбрасывал кадры.
В `WrtcPeer` используется единый атомарный счётчик кадров `frame_num = video_ts.fetch_add(1)`:
* `sequence_number = (frame_num & 0xFFFF) as u16`
* `pic_id = (frame_num & 0x7FFF) as u16`
* `timestamp = frame_num.wrapping_mul(300)` (шаг 300 тиков при частоте 90 кГц)

### 3.3. Отключение RTP-интерцепторов и тюнинг UDP-сокетов (`TunedTokioRuntime`)
* **Чистый `Registry::new()`:** В `WrtcPeer::create` отключены стандартные RTP-интерцепторы `webrtc-rs` (`NackResponder`, `NackGenerator`, `TWCC`). Это избавляет от клонирования каждого отправляемого RTP-пакета в кольцевой буфер ретрансляции и убирает блокировки мьютексов оценки полосы (BWE) на каждом пакете.
* **Увеличенные буферы ядра `SO_RCVBUF` / `SO_SNDBUF` (4 МиБ):** Кастомная среда выполнения `TunedTokioRuntime` перехватывает создание каждого UDP-сокета `webrtc-rs` в `wrap_udp_socket()` и через `socket2::SockRef` выставляет размер приёмного и передающего буферов сокета в `4 MiB` (`WEBRTC_UDP_SOCKET_BUFFER_SIZE`), исключая переполнение буфера ядра Linux/Windows/macOS при микровсплесках трафика.
* **Пул реакторов:** `PeerConnection` инициализируется с `with_dedicated_reactor_pool_size(4)` и `with_receive_mtu(1600)`.

### 3.4. Динамическая привязка видео-SSRC (`add_remote_video_ssrc`) и `ReceiverVideoConstraints`
* Когда JVB пересылает видеопоток участника, он использует SSRC, объявленный в Jingle (`session-initiate`, `source-add`, `description-info`) или в сообщениях `e2ee-ping` (`Discover`) / `e2ee-ack` (`Beacon`).
* Метод `WrtcPeer::add_remote_video_ssrc(ssrc)` динамически инжектирует `m=video` секцию (`mid=v_{ssrc}`, `a=sendonly`) в SDP через `append_remote_video_ssrc_to_sdp()` с рандомизированными UUIDv4 `msid`/`cname` и обновляет `RemoteDescription` / `LocalDescription`, привязывая входящий SSRC к выделенному `Recvonly`-трансиверу.
* При старте и обнаружении пиров отправляется сообщение `ReceiverVideoConstraints` (`lastN: -1`, `maxHeight: 2160`, `selectedEndpoints` / `onStageEndpoints`), гарантирующее, что SFU JVB форвардит видеопоток в полном объёме без троттлинга.
* Пока клиент не получил первый расшифрованный видеокадр (`client_video_warmed_up` / `first_client_rx`), пакеты параллельно страхуются отправкой через резервный канал (`DataChannel` / `Colibri-WS`), что обеспечивает мгновенное прохождение рукопожатия и первых пакетов до прогрева видеотракта JVB.

## 4. Стабильность сессий, детекция обрывов и очистка состояния

### 4.1. Устранение гонки маршрутизации при реконнекте (`session_id` ownership)
* **Проблема:** При переподключении клиента старый обработчик отключения мог удалить из `quic_router` и `clients_by_ip` запись уже новой сессии, получившей тот же VPN IP.
* **Решение:** В `ClientRegistry::remove_client` и `suspend_client` выполняется атомарная проверка `current.session_id == client_info.session_id` перед удалением маршрута из `quic_router` и `clients_by_ip`.

### 4.2. Мгновенная обработка XMPP MUC `presence unavailable` и закрытия сигналинга
* **На сервере:** При получении XMPP-станзы `<presence type="unavailable">` от участника комнаты сервер немедленно удаляет его из `clients_map`, `clients_by_tag`, `client_video_warmed_up` и вызывает `reg_clone.remove_client(&dead_client).await`, освобождая сессионный слот и IP без ожидания таймаута неактивности.
* **На клиенте:** Фоновая задача чтения XMPP отслеживает выход серверного occupant'а из комнаты и обрыв XMPP WebSocket, мгновенно пробуждая `failed_notify` для быстрого переподключения.

### 4.3. Сетевые таймауты и Watchdog состояния (`check_dead_reason`)
* Все операции чтения/записи и установки соединения по XMPP WebSocket и Colibri WebSocket защищены жёсткими таймаутами (`tokio::time::timeout`), что исключает зависание воркера при «полуоткрытых» TCP-соединениях.
* Метод `WrtcPeer::check_dead_reason()` вызывается каждые 2 секунды и принудительно перезапускает сессию, если:
  1. `PeerConnection` или `Colibri-WS` перешли в состояние `Failed` / `Closed`.
  2. `PeerConnection` находится в состоянии `Disconnected` дольше 8 секунд.
  3. Спустя 12 секунд после старта одновременно закрыты и `Colibri-WS`, и `SCTP DataChannel`.
* На клиенте дополнительно действует watchdog по `keepalive` / `keepalive-ack` (`WrtcMessage::Ping` / `WrtcMessage::Pong`), а сервер отвечает `keepalive-ack` только при условии, что сессия клиента числится активной в реестре (`reg_clone.is_session_active(&client_info.session_id)`).
* При любом выходе из цикла комнаты сервер гарантированно прерывает `video_uplink_task`, вызывает `reg_clone.remove_client()` для всех клиентов комнаты, закрывает `WrtcPeer` (`pc.close()` с таймаутом 3 с, в том числе в `Drop for WrtcPeer`) и отправляет `<presence type="unavailable">` в MUC.

## 5. Верификация через `tcpdump` и Wireshark

Для подтверждения того, что трафик маскируется под видеопоток, используется захват сетевых пакетов.

### Быстрая проверка в консоли:
```bash
# Проверка наличия RTP-заголовков (байт 0x80/0x90) на портах медиа-моста Ktalk
sudo tcpdump -ni any "udp and (net 89.169.16.0/24 or port 34788) and greater 200" -c 20 -X
```

### Запись и анализ дампа в Wireshark:
```bash
sudo tcpdump -ni any "udp and (net 89.169.16.0/24 or port 34788)" -w /tmp/wrtc_video.pcap -c 1000
```

### Характеристики трафика в дампе:
1. **ICE/STUN согласование:** Обмен пакетами STUN Binding Request / Response с атрибутом `USERNAME` (стек `ice4j.org` на стороне JVB).
2. **DTLS 1.2 Handshake:** Согласование ключей SRTP через `TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256`.
3. **Медиа-поток (RTP over SRTP):**
   * **Video Track:** Пакеты Payload Type `100` (или `96`, VP8) с тактовой частотой 90 кГц, монотонным приростом Timestamp (+300 на пакет) и фоновым keepalive 1 кадр/с при простое.
   * **Audio Keepalive:** Пакеты Payload Type `111` (Opus silence `0xf8, 0xff, 0xfe`) размером ~70–90 байт с интервалом 20 мс (48 кГц).

Для внешнего наблюдателя и систем DPI трафик полностью идентичен штатному видеозвонку в сервисе Ktalk / Jitsi.
