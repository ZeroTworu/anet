# Архитектура и спецификация транспорта `doh` (ASTP-L over DNS-over-HTTPS)

Документация актуальна для ветки `master`.

---

## 1. Введение и архитектурная концепция

### 1.1. Назначение
Транспорт `doh` (`dsn = "doh://domain?resolver=https://...&resolver=https://...&arq=true"`) — это транспорт "последней надежды" (Last Resort) для ANet VPN. Он спроектирован для работы в сетях с жесткими ограничениями связности и строгими правилами фильтрации, маскируя VPN-трафик под легитимные DNS-запросы к доверенным публичным DoH-резолверам (например, Yandex DNS `77.88.8.7` или AdGuard DNS) поверх зашифрованного HTTPS (TLS 1.3 / HTTP/2).

В отличие от прямых транспортов (QUIC, AHTTP, SSH, VNC, WebSocket), где клиент подключается непосредственно к IP-адресу VPN-сервера, в транспорте `doh` **клиент никогда не обращается к серверу ANet напрямую**:
* **На стороне клиента:** `reqwest::Client` (HTTP/2) общается с пулом доверенных DoH-серверов.
* **На стороне сервера:** `anet-server` слушает стандартный UDP-порт `53` и обрабатывает запросы, которые ему пересылает публичный резолвер благодаря стандартному механизму делегирования поддоменов (NS Glue Records).

### 1.2. Ключевые особенности реализации
1. **Невидимость для внешних инспекторов:** Провайдер видит исключительно стандартные зашифрованные TLS-сессии к доверенным IP-адресам публичных резолверов. Инспекция содержимого пакетов, истинного адреса назначения и внутреннего протокола невозможна.
2. **Нулевой крипто-оверхед (ASTP-L на ChaCha20-stream):** Из-за жестких лимитов длины DNS-запроса классический AEAD `ChaCha20Poly1305` (добавляющий 38 байт накладных расходов) заменен на поточный шифр **ChaCha20** без тега имитовставки Poly1305. Оверхед шифрования составляет **ровно 0 байт**. Ключ выводится из стандартного ASTP-хендшейка, а счетчик `Sequence` выступает в роли Nonce.
3. **Идентификация сессий (Session Demultiplexing):** Так как все пакеты от разных клиентов поступают на авторитативный сервер с IP-адресов одних и тех же резолверов, идентификатор клиентской сессии (`session_id`) кодируется непосредственно в заголовок чанка в имени поддомена.
4. **Многопутевая балансировка (Multi-Resolver Parallelism):** Поддержка пула нескольких DoH-резолверов с динамическим распределением чанков и непрерывным Health Check. Это предотвращает срабатывание ограничений частоты запросов (Rate Limiting) со стороны одного DNS-провайдера и повышает общую пропускную способность.
5. **Микро-ARQ (Selective Repeat):** Компенсирует потери пакетов на участке UDP:53 между публичным резолвером и VPN-сервером. Повторно пересылаются только утерянные чанки, исключая необходимость ретрансмиссии всего IP-пакета целиком.
6. **Микро-поллинг (Smart Long Polling):** Для обеспечения минимального RTT входящего (Downlink) трафика сервер удерживает пустые `poll`-запросы от клиента до 1.2 секунд, мгновенно отвечая на них при появлении пакетов в TUN-интерфейсе.
7. **HTTP/2 Мультиплексирование:** Фрагменты пакета отправляются параллельно в разных HTTP/2 стримах внутри постоянного TLS-соединения без блокировок Head-of-Line.

## 2. Схема маршрутизации и делегирования (Subdomain Delegation)

Для работы транспорта требуется базовая настройка DNS-инфраструктуры на стороне сервера:
1. В панели управления доменом создается `A`-запись (Glue Record): `ns1.anet-vpn.com -> IP_СЕРВЕРА`.
2. Создается `NS`-делегирование поддомена туннеля: `t1.anet-vpn.com -> ns1.anet-vpn.com`.

```text
+-------------------+      1. POST /dns-query (HTTP/2)      +--------------------+
|    anet-client    |      Q: <session>.<data>.t1.domain    | Public DoH Servers |
|  (reqwest H2/TLS) |======================================>| (e.g., 77.88.8.7)  |
+-------------------+                                       +--------------------+
          ^                                                           |
          | 4. HTTP/2 200 OK                                          | 2. UDP Port 53
          |    TXT: "Base64_Encoded_Payload"                          |    Q: <session>.<data>...
          |                                                           V
+-------------------+                                       +--------------------+
|    anet-client    |      3. UDP Port 53 (Response)        |    anet-server     |
|   (TUN Inject)    |<--------------------------------------|    (UDP:53 Bind)   |
+-------------------+         TXT: "Base64..."              +--------------------+
```

## 3. Структура пакетов на уровне сети (Wire Format)

Из-за фундаментальной асимметрии протокола DNS форматы Uplink и Downlink существенно различаются.

### 3.1. Uplink (Клиент $\to$ Сервер) — Запросы `TXT` в имени домена
Максимальная длина FQDN — 253 символа. Длина одного лейбла (между точками) — до 63 символов.
IPv4/IPv6 пакет шифруется (ChaCha20) и нарезается на чанки.

**Заголовок чанка (10 байт):**
```text
+-------------------+-------------------+-------------------+-------------------+
| Session ID (4 Б)  | Sequence (4 Б)    | Chunk Index (1 Б) | Total Chunks (1 Б)|
| u32 Big-Endian    | u32 Big-Endian    | u8 (0 .. total-1) | u8 (1 .. N)       |
+-------------------+-------------------+-------------------+-------------------+
```
* `Session ID`: уникальный 32-битный идентификатор сессии, выделенный на этапе Handshake, позволяющий серверу демультиплексировать клиентов за одним публичным резолвером.
* `Sequence`: уникальный порядковый номер пакета (используется для Nonce и Reassembly).
* `Chunk Index / Total Chunks`: параметры сборки фрагментов.

**Кодирование (Base32):**
Заголовок (10 байт) + Полезная нагрузка (до $M$ байт) кодируются в **Base32 без паддинга** (RFC 4648, алфавит `abcdefghijklmnopqrstuvwxyz234567`, регистронезависимый).
Строка разбивается точками каждые 63 символа, после чего к ней добавляется суффикс зоны.

**Динамический расчет размера чанка:**
$$M = \left\lfloor \frac{(253 - L_{\text{zone}} - N_{\text{dots}}) \times 5}{8} \right\rfloor - 10$$
где $L_{\text{zone}}$ — длина базовой зоны (например, `.t1.anet-vpn.com` = 16 символов), $N_{\text{dots}}$ — число разделяющих точек. Для стандартной зоны это обеспечивает полезную нагрузку около 130–135 байт на чанк.

### 3.2. Downlink (Сервер $\to$ Клиент) — Ответы `TXT`
С учетом требований **DNS Flag Day** максимальный размер буфера EDNS0 принимается равным **1232 байта**, чтобы исключить IP-фрагментацию в магистральных сетях.
Целый IPv4-пакет + 4 байта `Sequence` шифруются и кодируются в **Base64**.

**Ограничения DNS TXT:**
Одна строка (String) внутри TXT-записи ограничена 255 байтами согласно RFC 1035. Сервер разбивает длинный Base64-ответ на массив строк:
```text
TXT: [ "Base64_Chunk_1...", "Base64_Chunk_2...", "Base64_Chunk_3..." ]
```
Клиент и резолвер склеивают строки массива в единый буфер перед декодированием.

## 4. Криптография: ASTP-L (ChaCha20-Stream)

Для обеспечения строгой криптографической стойкости без увеличения размера пакетов:

1. **Инициализация сессии (Handshake):**
   * Клиент и сервер выполняют стандартный ASTP-хендшейк (Phase I–IV), фрагментированный через базовые чанки.
   * На шаге Phase IV клиент и сервер вырабатывают общий секрет `shared_key` (32 байта) и `session_id` (4 байта).
2. **Шифрование Data Plane (ChaCha20):**
   * Для каждого IP-пакета используется уникальный монотонно растущий `Sequence Number` (u32).
   * 12-байтный Nonce формируется детерминированно:
     $$\text{Nonce} = [\text{Sequence (4 Б Big-Endian)}] \,||\, [\text{Session ID (4 Б)}] \,||\, [0x00, 0x00, 0x00, 0x00]$$
   * Полезная нагрузка ксорится с генерируемым ключевым потоком `ChaCha20(shared_key, nonce)`.
   * **Оверхед шифрования:** 0 байт.

## 5. Механизмы оптимизации и удержания соединения

### 5.1. Пул резолверов и балансировка (Multi-Resolver Parallelism)
Клиент держит HTTP/2 пул соединений к нескольким независимым DoH-резолверам.
* Чанки одного большого пакета распределяются round-robin / least-loaded между разными DoH-провайдерами.
* Фоновый сторож (Health Checker) с интервалом в 30 секунд замеряет RTT и исключает резолверы, возвращающие ошибки (`SERVFAIL`, `REFUSED`) или имеющие высокую задержку.

### 5.2. Микро-ARQ (Selective Repeat)
Для компенсации потерь UDP-пакетов между публичным резолвером и авторитативным сервером:
* В Downlink-ответах сервер может возвращать битовую маску принятых чанков (ACK mask).
* Клиент отслеживает тайм-ауты неподтвержденных чанков (RTO ~ 400–600 мс) и повторно отправляет **только недостающие чанки**, не перезагружая туннель повтором всего пакета.

### 5.3. Защита от DNS-кэширования
* Все ответы сервера отдаются со строгим **`TTL = 0`** (или `TTL = 1` для резолверов с принудительным минимумом).
* Имена `poll`-запросов всегда содержат криптографический Nonce:
  `poll.<session_id>.<nonce_hex>.t1.anet-vpn.com`
  Это гарантирует, что резолвер всегда отправит запрос на авторитативный сервер, а не отдаст закэшированный пустой ответ.

### 5.4. Совместимость с DNS 0x20 Bit Encoding
Публичные резолверы используют случайный регистр букв в запросах к авторитетным серверам для защиты от отравления кэша (0x20 encoding):
* **Сервер обязан:**
  1. Приводить имя запроса к нижнему регистру перед декодированием Base32.
  2. В секции `Question` ответа возвращать доменное имя **в том же регистре символов**, в каком оно пришло от резолвера, иначе ответ будет отброшен резолвером как невалидный.

### 5.5. Микро-поллинг (Smart Long Polling)
1. Клиент непрерывно поддерживает 2–3 параллельных активных `poll`-запроса.
2. При поступлении `poll` сервер проверяет исходящую очередь пакетов клиента (`router_rx`).
3. При наличии пакета сервер немедленно формирует ответ.
4. При отсутствии пакетов сервер асинхронно удерживает запрос (через `tokio::time::timeout`) до **1200 мс**.
5. Если в течение этого интервала из TUN поступает пакет — он немедленно отправляется в удерживаемый запрос; по истечении 1200 мс возвращается пустой ответ (или `NODATA`).

## 6. Конфигурация

### 6.1. Настройка клиента (`client.toml`)
Вся конфигурация транспорта инкапсулирована непосредственно в Query-параметрах `dsn` (по аналогии с AHTTP и WebRTC), что исключает необходимость добавления лишних полей в структуры `ServerConfig` и модель БД:

```toml
[[servers]]
name = "DoH Emergency Tunnel"
# Формат DSN:
# doh://<доменная_зона>?resolver=<url1>&resolver=<url2>&arq=<bool>&dup_hs=<bool>&hold_ms=<ms>
#
# Параметры Query:
# - `resolver`: URL публичного DoH-резолвера (может повторяться несколько раз для пула)
# - `arq`: включение микро-ARQ (Selective Repeat) при потерях на плече UDP:53 (по умолчанию true)
# - `dup_hs`: дублирование чанков хендшейка через разные резолверы для быстрого RTT (по умолчанию true)
# - `hold_ms`: желаемое время удержания long-poll запроса (по умолчанию 1200)
dsn = "doh://t1.anet-vpn.com?resolver=https://77.88.8.7/dns-query&resolver=https://dns.adguard-dns.com/dns-query&arq=true&dup_hs=true"
timeout_secs = 10
server_pub_key = "<BASE64_ED25519_PUBLIC_KEY>"
```

### 6.2. Настройка сервера (`server.toml`)
```toml
[server]
# Сервер слушает стандартный UDP-порт 53
doh_bind_to = "0.0.0.0:53"

[doh_transport]
# Авторитативная зона, делегированная на данный сервер
domain = "t1.anet-vpn.com"
# Максимальное время удержания long-poll запроса (в мс)
poll_hold_timeout_ms = 1200
```

## 7. Модульная структура реализации

1. **`anet-common/src/base32.rs`**: Высокопроизводительный RFC 4648 Base32 кодер/декодер без паддинга.
2. **`anet-common/src/astp_lite.rs`**: Реализация поточного режима `ChaCha20` с нулевым оверхедом и детерминированным Nonce.
3. **`anet-common/src/doh_chunking.rs`**: Нарезка IP-пакетов с динамическим расчетом под длину зоны и очередь сборки `ReassemblyQueue` с ARQ.
4. **`anet-client-core/src/transport/doh.rs`**: Реализация `ClientTransport`. Управление пулом HTTP/2 DoH-резолверов, multi-path балансировка и `poll`-менеджер.
5. **`anet-server/src/servers/doh_dns.rs`**: Высокопроизводительный UDP:53 сервер. RFC 1035 парсер, поддержка 0x20 encoding, long-poll удержание и маршрутизация в `ClientRegistry`.
