# Архитектура и спецификация транспорта `doh` (ASTP-L over DoH / Hybrid UDP DNS)

Документация актуальна для ветки `dev/doh`.

---

## 1. Введение и архитектурная концепция

### 1.1. Назначение
Транспорт `doh` (`dsn = "doh://domain?resolver=doh://...&resolver=udp://...&arq=true&dup=2&hold_ms=25"`) — это отказоустойчивый DNS-туннель «последней надежды» (Last Resort) для ANet VPN. Он спроектирован для работы в сетях с жёсткими ограничениями связности, ТСПУ/DPI-фильтрацией и блокировкой прямых соединений до зарубежных IP-адресов.

В отличие от прямых транспортов (`quic://`, `https://` AHTTP, `ssh://`, `vnc://`, `ws://`/`wss://`, `wrtc://`), где клиент подключается непосредственно к IP-адресу VPN-сервера или CDN, в транспорте `doh` **клиент никогда не обращается к IP-адресу сервера ANet напрямую**:
* **На стороне клиента:** Диспетчер параллельно отправляет DNS-запросы через пул публичных рекурсивных резолверов (поддерживаются как зашифрованные **DoH-резолверы `doh://`** поверх TLS 1.3 / HTTP/2, так и классические **UDP-резолверы `udp://`** на порту 53).
* **На стороне сервера:** `anet-server` слушает стандартный UDP-порт `53` в качестве авторитетного (Authoritative) NS-сервера доменной зоны и принимает запросы от рекурсивных резолверов через стандартный механизм делегирования поддоменов (NS Glue Records).

---

### 1.2. Ключевые механизмы (V2 Architecture)

1. **Двусторонний канальный ARQ (Downlink SACK + Uplink Selective Repeat / NACK):**
   Рекурсивные DNS-резолверы работают поверх ненадёжного UDP и регулярно теряют или переупорядочивают 10–20% пакетов. Чтобы ядро ОС внутри TUN-интерфейса не видело потерь и не сбрасывало окно TCP (`cwnd`), транспорт реализует собственный канальный уровень гарантированной доставки:
   * **Downlink ARQ Window + Дедупликация ретраев резолвера (Пункт 1):** Сервер не удаляет пакеты из очереди при первой отправке, а хранит их в окне неподтверждённых фреймов (`DownlinkArqWindow`) до получения кумулятивного `ack_seq` и битовой маски `sack_bitmap` от клиента. Повторные UDP-ретраи от рекурсивных резолверов обслуживаются из кольцевого кэша `RecentDnsResponses` без потери пакетов. На клиенте `DownlinkReorderBuffer` выравнивает порядок пакетов перед записью в TUN.
   * **Uplink Per-Chunk ARQ / NACK (Пункт 2):** Каждый Uplink-чанк отслеживается в `UplinkArqState`. Сервер возвращает в каждом ответе кумулятивный `uplink_ack_seq` и битовые маски недостающих чанков незавершённых пакетов (`NACK`). При потере одного чанка клиент досылает **только потерянный чанк** через другой резолвер.

2. **Адаптивное проактивное дублирование пакетов (`dup`, Пункт 3):**
   По аналогии с архитектурой `MasterDnsVPN`, критичные и одночанковые пакеты (хендшейки, ICMP `ping`, TCP `SYN`/`ACK`, внутритуннельный DNS) проактивно отправляются в `dup=2` (до `3`) копиях через **разные** резолверы параллельно (Tail-Latency Hedging). При вероятности потери на одном резолвере $p = 15\%$ отправка двух копий снижает итоговые потери до $p^2 = 2.25\%$, а трёх — до $0.3\%$, устраняя скачки пинга.

3. **Компактный Wire Format + Base36 + LZ4 + Multi-TXT (Пункт 4):**
   * **Нулевой крипто-оверхед (`ASTP-L` ChaCha20-stream):** Поточный шифр ChaCha20 с детерминированным Nonce из `(sequence, session_id)` добавляет **0 байт** криптографического оверхеда.
   * **Компактный заголовок и кодирование Base36 (`0-9a-z`):** Поддержка плотного регистронезависимого кодирования Base36 (5.17 бит/символ) и опционального сжатия полезной нагрузки `LZ4` перед фрагментацией.
   * **Multi-TXT ответы повышенной ёмкости:** На Downlink сервер упаковывает данные в серию 255-байтных сегментов внутри TXT RDATA с поддержкой EDNS0, позволяя доставлять крупные пакеты и пачки за минимальное число DNS-транзакций.

4. **Мгновенный отклик (`hold_ms = 25`), флаг `MORE_DATA_PENDING` и Least-Loss балансировка (Пункт 5):**
   * Отказ от длительного удержания запросов (`1200 мс`) на авторитативном сервере предотвращает срабатывание внутренних UDP-ретраев и RTT-пессимизации (infra-cache throttling) на рекурсивных резолверах (Yandex, Google, Cloudflare).
   * Сервер отвечает за `0..25 мс` и выставляет в заголовке ответа бит `MORE_DATA_PENDING`, если в очереди сессии остались ещё пакеты. Клиентский **Adaptive Poll Pacer** при виде этого флага мгновенно выстреливает каскадом параллельных опросов, вычерпывая очередь сервера на максимальной скорости.
   * Балансировщик `ResolverPool` непрерывно считает скользящий `EMA RTT` и `loss_rate` каждого резолвера, направляя трафик через узлы с наименьшими потерями (`Least-Loss + RTT Score`).

5. **Гибридный пул резолверов (`doh://` + `udp://`, Пункт 6):**
   В рамках одной сессии `dsn = "doh://..."` клиент может одновременно использовать как зашифрованные DoH-резолверы (`resolver=doh://77.88.8.8/dns-query`), так и прямые UDP:53 резолверы (`resolver=udp://77.88.8.8:53`), полностью избегая TCP-over-TCP Head-of-Line blocking там, где UDP:53 доступен.

## 2. Схема маршрутизации и делегирования (Subdomain Delegation)

Для работы транспорта требуется настройка DNS-записей у регистратора домена:
1. Создаётся `A`-запись (Glue Record): `ns1.anet-project.org -> IP_ВАШЕГО_VPS`.
2. Создаётся `NS`-делегирование поддомена туннеля: `t1.anet-project.org -> ns1.anet-project.org`.

```text
+--------------------+   1a. DoH (HTTPS POST /dns-query)   +-----------------------+
|                    |====================================>| Public DoH Resolvers  |
|    anet-client     |                                     | (doh://77.88.8.7/...) |
| (Hybrid Dispatcher)|   1b. Raw UDP:53 DNS Query          +-----------------------+
|  ARQ + Hedging +   |------------------------------------>| Public UDP Resolvers  |
|  Least-Loss Pool   |                                     | (udp://77.88.8.8:53)  |
+--------------------+                                     +-----------------------+
          ^                                                            |
          | 4. DNS TXT Response (Seq + Flags +                         | 2. Authoritative UDP:53
          |    Uplink ACK/NACK + Encrypted Batch)                      |    Q: <labels>.t1.domain
          |                                                            V
+--------------------+                                     +-----------------------+
|    anet-client     |   3. Instant UDP:53 TXT Reply       |      anet-server      |
| (Reorder + Inject) |<------------------------------------|   (UDP:53 Auth DNS)   |
+--------------------+      (0..25ms + Dedup Cache)        +-----------------------+
```

## 3. Структура пакетов на уровне сети (Wire Format)

### 3.1. Uplink (Клиент $\to$ Сервер) — Запросы `TXT` в QNAME
Максимальная длина FQDN — 253 символа, длина одного лейбла — до 63 символов.

**Типы запросов в префиксе QNAME:**
1. **Хендшейк (`hs.`):** `hs.<temp_sid_hex>.<idx>.<total>.<encoded_labels>.<zone>`
2. **Опрос и подтверждение Downlink (`poll.`):** `poll.<sid_hex>.<dl_ack_hex>.<dl_sack_hex>.<nonce_hex>.<zone>`
3. **Данные и обратная связь (`Data Chunk`):** `<encoded_labels>.<zone>`

Внутри каждого чанка данных передаётся заголовок с `session_id`, `sequence`, индексом чанка `(chunk_index, total_chunks)` и встроенным подтверждением получения Downlink-фреймов (`dl_ack_seq`, `dl_sack_bitmap`), чтобы сервер получал обратную связь даже без отдельных `poll`-запросов.

### 3.2. Downlink (Сервер $\to$ Клиент) — Ответы `TXT`
Каждый ответ сервера в секции `TXT` несёт бинарный фрейм (в Base64), содержащий:
* **`dl_seq` (`u32`):** Порядковый номер Downlink-фрейма для `DownlinkArqWindow` и клиентского `DownlinkReorderBuffer`.
* **`flags` (`u8`):**
  * `bit 0` (`0x01`): `MORE_DATA_PENDING` — сигнализирует клиенту, что в очереди сервера ещё есть готовые пакеты и нужно немедленно отправить дополнительные `poll`-запросы.
  * `bit 1` (`0x02`): `HAS_UPLINK_FEEDBACK` — указывает на наличие блока подтверждений Uplink ARQ/NACK.
* **`uplink_feedback` (при наличии флага `HAS_UPLINK_FEEDBACK`):**
  * `ul_cum_ack` (`u32`) — кумулятивный номер последнего полностью собранного Uplink-пакета.
  * Список NACK-масок для незавершённых многочанковых пакетов `(pkt_seq: u16, received_mask: u16)`.
* **Зашифрованная полезная нагрузка (`ChaCha20`):**
  * Одиночный IPv4/IPv6 пакет,
  * Пачка склеенных пакетов (`0x00` + `[len_be16, pkt]...`),
  * Или фрагмент крупного пакета (`0x01` + `pkt_id_be16, frag_idx, total_frags, data...`).

## 4. Конфигурация

### 4.1. Настройка клиента (`client.toml`)
Внешняя схема DSN всегда **`doh://`** (так как схема `https://` зарезервирована за транспортом `AHTTP`). Внутри параметра `resolver=` поддерживаются схемы:
* `doh://host/dns-query` — DNS-over-HTTPS (поверх TLS / HTTP/2),
* `https://host/dns-query` — синоним `doh://` для обратной совместимости в параметре `resolver`,
* `udp://ip:53` — классический быстрый UDP DNS без накладных расходов TCP/TLS.

```toml
[stealth]
# Полиморфный TLS-отпечаток BoringSSL (Chrome / Firefox / Safari / Randomized)
# и защита от активного спуфинга сертификатов публичных DoH-резолверов (по умолчанию: true)
tls_fingerprint = "auto"
tls_verify_peer = true

[[servers]]
name = "FN First [DOH]"
# Формат DSN:
# doh://<доменная_зона>?resolver=<doh_or_udp_url>&arq=<bool>&dup=<1..3>&dup_hs=<bool>&hold_ms=<ms>
#
# Параметры Query:
# - `resolver`: адрес резолвера (`doh://77.88.8.7/dns-query` или `udp://77.88.8.8:53`). Указывается несколько раз.
# - `arq`: включение двустороннего канального ARQ/SACK/NACK (по умолчанию true)
# - `dup`: коэффициент проактивного дублирования приоритетных пакетов через разные резолверы (по умолчанию 2)
# - `dup_hs`: дублирование пакетов хендшейка через разные резолверы (по умолчанию true)
# - `hold_ms`: время микро-коалесцинга poll-запроса на сервере в мс (рекомендуется 20..35, по умолчанию 25)
dsn = "doh://t1.anet-project.org?resolver=doh://77.88.8.7/dns-query&resolver=doh://77.88.8.8/dns-query&resolver=udp://77.88.8.1:53&resolver=udp://77.88.8.2:53&arq=true&dup=2&dup_hs=true&hold_ms=25"
timeout_secs = 10
server_pub_key = "<BASE64_ED25519_PUBLIC_KEY>"
```

### 4.2. Настройка сервера (`server.toml`)
```toml
[server]
# Сервер слушает стандартный UDP-порт 53
doh_bind_to = "0.0.0.0:53"

[doh_transport]
# Авторитативная зона, делегированная на данный сервер через NS-запись
domain = "t1.anet-project.org"
# Максимальное время микро-удержания poll-запроса (в мс).
# Рекомендуется 20..35 мс, чтобы рекурсивные резолверы не делали UDP-ретраев и не пессимизировали зону.
poll_hold_timeout_ms = 25
```
