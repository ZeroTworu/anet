# wss:// транспорт: топология и настройка

## Схема развёртывания

```
[клиент] --wss://--> [ТСПУ / красная зона]
         --wss://--> [белый IP в облаке: nginx + настоящий TLS-сертификат]
         --ws://-->  [серая зона]
                 --> [anet_server]
                 --> [чистый интернет]
```

`anet_server` **никогда не видит TLS** — он всегда слушает обычный `ws://`
на внутреннем адресе (`server.websocket_bind_to`). Вся TLS-граница вынесена
на nginx (или Caddy) на белом IP.

## Почему TLS не реализован внутри anet_server

Может показаться, что проще один раз завершать TLS прямо в `anet_server` —
но у этого подхода два серьёзных недостатка именно с точки зрения обхода
активного зондирования (ТСПУ, GFW и подобные системы):

1. **Самоподписанный сертификат — сам по себе red flag.** Активное
   зондирование не просто пассивно слушает трафик — оно коннектится к
   подозрительному IP:443 напрямую и проверяет, настоящий ли это сайт.
   Self-signed сертификат без цепочки до публичного CA — один из самых
   частых сигналов "это не обычный веб-сервер". Настоящий сертификат
   Let's Encrypt через nginx полностью снимает эту проблему.
2. **Нет decoy-контента.** nginx может отдавать на всех путях, кроме
   ASTP-пути, безобидный сайт-прикрытие. Голый `anet_server` с TLS отвечает
   одинаково на любой путь — тоже заметный паттерн при активном зондировании.

Поэтому нативная поддержка TLS в `anet_server` **сознательно не
реализовывалась** — вся маскировка под HTTPS должна происходить на
edge-узле (nginx/Caddy) с настоящим сертификатом, а не внутри бинарника
`anet_server`.

## Почему серая зона (nginx → anet_server) остаётся на ws://, а не wss://

Полезная нагрузка уже зашифрована на уровне ASTP (X25519 для рукопожатия,
ChaCha20Poly1305 — для трафика) внутри WebSocket-фреймов. Оборачивание этого
шифротекста ещё и в TLS между nginx и anet_server не добавляет
конфиденциальности данных — только накладные расходы. Единственное, что
здесь имеет значение — насколько сама серая зона доверенная как
транспортный сегмент (частная сеть/VPN между белым IP и сервером или голый
интернет); это вопрос инфраструктуры, а не кода.

## Настройка

### 1. Клиент (`client.toml`)

В `dsn` сервера просто укажите схему `wss://` вместо `ws://`:

```toml
[[servers]]
dsn = "wss://example.com/your_websocket_path"
```

Транспортный слой сам выберет TLS-коннектор по схеме — никаких
дополнительных полей конфига не требуется. Проверка сертификата сервера
на этом транспорте намеренно отключена (`AcceptAnyServerCert`): доверие к
узлу обеспечивается ASTP-рукопожатием (X25519 + подпись Ed25519), а не
TLS-цепочкой — TLS здесь исключительно камуфляж под обычный HTTPS-трафик
для DPI, а не граница доверия. Это та же модель, что уже используется в
QUIC-транспорте.

### 2. nginx на белом IP

См. `contrib/config/nginx-wss-example.conf`. Ключевые моменты:

- реальный сертификат через `certbot --nginx -d example.com` (не
  самоподписанный);
- `location` для ASTP-пути с корректными заголовками апгрейда
  (`Upgrade`, `Connection: upgrade`) и увеличенным `proxy_read_timeout`
  (WS-сессия долгоживущая, дефолтный таймаут nginx её оборвёт);
- на всех остальных путях — decoy-сайт, а не 404/пустой ответ.

Не забудьте про автопродление сертификата (`certbot renew` через
systemd-таймер/cron — обычно уже настраивается самим certbot при установке).

### 3. anet_server

Никаких изменений в конфиге сервера не требуется — `server.websocket_bind_to`
и `server.websocket_path` работают так же, как для обычного `ws://`;
сервер просто не знает, что перед ним стоит TLS-терминирующий прокси.

## Заметка про ALPN

В `wss_connector()` TLS-клиент явно объявляет ALPN `["h2", "http/1.1"]` —
как это делает обычный браузер. Список из одного `http/1.1` — заметная
аномалия ещё на этапе ClientHello, до WebSocket-апгрейда, поэтому
использовать оба протокола важно именно для правдоподобности маскировки.
